**Status:** Normative (MCP++ 1.0 current MCP application binding)  
**Task:** MCPP-021  
**Authority:** ADR-0006 (Accepted); plan KD-2, KD-3; gates 3–4; MCPP-G030  
**MCP revision:** `2026-07-28`  
**Binding id:** `mcp-binding/2026-07-28`  
**Interface label:** `McpBinding20260728@1`  
**Primary sources:** [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28), [base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic), [versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), [server/discover](https://modelcontextprotocol.io/specification/2026-07-28/server/discover); verification note MCPP-010 (`docs/reports/mcplusplus-1.0-gap-closure/baseline/official-mcp-a2a.md`)

## 1. Purpose

This document is the **current** MCP application binding for MCP++ 1.0. It maps
abstract Profiles A–H onto the official modern MCP revision `2026-07-28`:

- **Stateless** per-request processing (no protocol-level session).
- Version, client capabilities, and identity ride in request `_meta`.
- Servers implement `server/discover`; clients **MAY** call it first.
- The removed `initialize` / `notifications/initialized` exchange is **not**
  part of this binding.

This binding does **not** redefine Profile A–H object models, CID rules, UCAN
validation, policy evaluation, Event DAG structure, or payment objects. Those
remain in the abstract profile registry and profile chapters.

## 2. Normative keywords

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY**
are to be interpreted as described in RFC 2119.

## 4. Lifecycle (normative)

### 4.1 Statelessness

MCP under this binding is a **stateless protocol** (official base protocol):

1. Every request carries all information needed to process it.
2. The server processes each request independently; no protocol state may be
   inferred from previous requests on the same connection or stream.
3. Open connections (including stdio processes and libp2p streams) are **not**
   MCP application sessions under this binding.
4. Application state that spans requests **MUST** be referenced by an explicit
   identifier the client passes on each request (see §9 State handles).

### 4.2 No initialize handshake

The following methods are **not** part of `mcp-binding/2026-07-28`:

| Method | Status on this binding |
| --- | --- |
| `initialize` | **Forbidden.** MUST be rejected when the peer claims only this binding |
| `notifications/initialized` | **Forbidden.** MUST be rejected (or ignored without establishing session semantics) when the peer claims only this binding |
| Legacy `Mcp-Session-Id` session model | **Not used** for modern requests under this binding |

**Initialize-as-current is non-conformant.** A client or server that sends or
accepts `initialize` / `notifications/initialized` while advertising only
`mcp-binding/2026-07-28` (or while asserting `protocolVersion` `2026-07-28` as
the active modern path) **MUST** be treated as failing closed for current-binding
conformance claims.

A **current-only** server (this binding, no legacy path) that receives
`initialize` **MUST** reject it with a JSON-RPC error. The server **SHOULD**
include the modern versions it supports (at least `2026-07-28`) in the error
payload so legacy clients can surface a diagnostic. Recommended shape:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32601,
    "message": "initialize is not supported under mcp-binding/2026-07-28",
    "data": {
      "bindingId": "mcp-binding/2026-07-28",
      "supportedVersions": ["2026-07-28"],
      "reason": "initialize_as_current_rejected"
    }
  }
}
```

Exact error codes for unknown methods are implementation-defined in the official
MCP compatibility matrix; the **rejection** and the **supportedVersions**
diagnostic are normative for MCP++ current-only peers.

### 4.3 Discovery is not initialize

Servers **MUST** implement `server/discover` (official MCP requirement). Clients
**MAY** call it before other RPCs. Discovery:

- **MUST NOT** be treated as a mandatory handshake.
- **MUST NOT** create a protocol-level session.
- **MUST NOT** substitute for the removed initialize exchange.

A client that never calls `server/discover` and instead issues application RPCs
with correct per-request `_meta` **MUST** be accepted when the version and
required metadata are valid.

## 5. Per-request metadata (normative)

### 5.1 Placement

Official MCP carries protocol fields on `params._meta` (JSON-RPC params object).
Implementations **MUST** accept this placement. HTTP streamable transport also
carries the version in the `MCP-Protocol-Version` header (see §8).

### 5.2 Required client request `_meta` keys

Every client request under this binding **MUST** include:

| Key | Type | Required | Description |
| --- | --- | --- | --- |
| `io.modelcontextprotocol/protocolVersion` | string | **Yes** | Must be `2026-07-28` for this binding |
| `io.modelcontextprotocol/clientCapabilities` | object | **Yes** | Client capabilities relevant to this request |

Clients **SHOULD** include:

| Key | Type | Description |
| --- | --- | --- |
| `io.modelcontextprotocol/clientInfo` | object `{name, version}` | Client identity for display/logging |

A request missing any required key **MUST** be rejected with JSON-RPC
`-32602` (Invalid params). On HTTP, the response status **MUST** be
`400 Bad Request` when the transport binding requires it.

### 5.3 Protocol version acceptance

| Condition | Server behavior |
| --- | --- |
| `protocolVersion` is `2026-07-28` and this binding is offered | Accept (subject to other validation) |
| `protocolVersion` is missing | Reject `-32602` |
| `protocolVersion` is a known unsupported or undeclared revision | Reject with `UnsupportedProtocolVersion` (`-32022`) listing supported versions |
| Client claims this binding id with a non-`2026-07-28` version | Reject fail-closed (forgery / mismatch) |

`UnsupportedProtocolVersion` error shape (official):

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32022,
    "message": "Unsupported protocol version",
    "data": {
      "supported": ["2026-07-28"],
      "requested": "<client version>"
    }
  }
}
```

### 5.4 Server result `_meta`

Servers **SHOULD** include on each successful result:

| Key | Type | Description |
| --- | --- | --- |
| `io.modelcontextprotocol/serverInfo` | object `{name, version}` | Server identity |

Servers **SHOULD** also echo binding advertisement when MCP++ profiles are in
use (see §6).

### 5.5 Binding advertisement key (MCP++)

MCP++ peers using this binding **MUST** be able to name the binding explicitly.
Normative advertisement keys for MCP++ 1.0:

| Locus | Key / field | Value |
| --- | --- | --- |
| Request `_meta` (client **SHOULD**) | `io.mcplusplus/bindingId` | `mcp-binding/2026-07-28` |
| Discover / capability maps (server **MUST** when claiming MCP++ 1.0) | `bindingId` or equivalent under `capabilities["mcp++"]` | `mcp-binding/2026-07-28` |

Supporting modern `_meta` alone without naming the binding id is discouraged
for dual-binding fleets; dual-peer and forgery proofs live in MCPP-022.

## 6. Profile capability placement (normative)

Abstract profile keys are defined in the parent registry and are
**MCP-version-independent**:

| Key | Profile |
| --- | --- |
| `mcp++/mcp-idl` | A |
| `mcp++/cid-envelope` | B |
| `mcp++/ucan` | C |
| `mcp++/deontic-policy` | D |
| `mcp++/p2p-transport` | E (optional transport) |
| `mcp++/event-dag` | F |
| `mcp++/risk-scheduling` | G |
| `mcp++/x402-payments` | H |

### 6.1 Client advertisement (per request)

Under this binding, profile support the client wishes to use **MUST** be
present on the request that needs those profiles. Placement **MUST** be one of:

1. **Preferred:** under
   `params._meta["io.modelcontextprotocol/clientCapabilities"].extensions["io.mcplusplus/profiles"]`
   as a map of abstract keys to `true` or settings objects; or
2. **Equivalent:** under
   `params._meta["io.modelcontextprotocol/clientCapabilities"]["mcp++"].profiles`
   as a list or map of the same abstract keys.

Empty client capabilities are legal for baseline MCP methods that do not
require MCP++ profiles.

### 6.2 Server advertisement (discover and results)

Servers that claim MCP++ profiles under this binding **MUST** advertise them
via `server/discover` capabilities using the same abstract keys (map or nested
`mcp++.profiles` form). Profile support is therefore available **per request**
(client `_meta`) and/or **via discovery** (server capabilities)—never via a
session initialize result on this path.

### 6.3 Official MCP extensions

Extension identifiers under `capabilities.extensions` **MUST** follow official
`_meta` key naming (reverse-DNS with slash, mandatory prefix). Examples relevant
to this binding:

| Extension id | Role |
| --- | --- |
| `io.modelcontextprotocol/tasks` | Official MCP Tasks extension (poll `tasks/get`, update `tasks/update`) |
| `io.mcplusplus/profiles` | MCP++ abstract profile map (this binding’s preferred nest) |

MCP extension ids are **not** A2A extension URIs. A2A uses
`https://mcplusplus.io/extensions/execution/v1` (ADR-0006); that URI is out of
scope for this MCP binding document except as a non-colliding identifier space.

## 7. Discovery (`server/discover`)

### 7.1 Request

Clients send `server/discover` with standard required `_meta` and **no** other
mandatory body parameters:

```json
{
  "jsonrpc": "2.0",
  "id": "discover-1",
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "example-client",
        "version": "1.0.0"
      },
      "io.mcplusplus/bindingId": "mcp-binding/2026-07-28"
    }
  }
}
```

### 7.2 Result

Servers **MUST** return at least:

| Field | Requirement |
| --- | --- |
| `resultType` | `complete` (or official result typing rules) |
| `supportedVersions` | Includes `2026-07-28` |
| `capabilities` | Server capability map, including MCP++ profile keys when claimed |
| `result._meta["io.modelcontextprotocol/serverInfo"]` | **SHOULD** be present |

MCP++ current-only servers **MUST** include binding identity in the discover
result, for example:

```json
{
  "resultType": "complete",
  "supportedVersions": ["2026-07-28"],
  "capabilities": {
    "tools": {},
    "extensions": {
      "io.modelcontextprotocol/tasks": {},
      "io.mcplusplus/profiles": {
        "mcp++/mcp-idl": true,
        "mcp++/cid-envelope": true
      }
    },
    "mcp++": {
      "bindingId": "mcp-binding/2026-07-28",
      "profiles": ["mcp++/mcp-idl", "mcp++/cid-envelope"]
    }
  },
  "_meta": {
    "io.modelcontextprotocol/serverInfo": {
      "name": "mcp++-current",
      "version": "1.0.0"
    }
  }
}
```

## 8. HTTP streamable transport notes

When carried over Streamable HTTP (official transport), modern requests
additionally use:

| Header | Role |
| --- | --- |
| `MCP-Protocol-Version` | Protocol version (must match request `_meta` version) |
| `Mcp-Method` | Method name (official minor change for 2026-07-28) |
| `Mcp-Name` | Resource/tool/prompt name when applicable |

Header / body version mismatch **MUST** fail closed (`HeaderMismatch` /
`-32020` or transport `400` per official server validation). This binding does
not reintroduce `Mcp-Session-Id` as a modern session handshake.

## 9. State handles map to `StateRef`

Official modern MCP requires multi-request application state to be referenced by
an **explicit identifier** on each request—not by connection identity.

For MCP++ under this binding:

1. Any opaque MCP state handle, task continuation token, or application-level
   handle that denotes shared mutable or content-addressed state **MUST** be
   mappable to a `StateRef@1` (or a documented precursor object that declares
   the same mode discipline).
2. `StateRef@1` **MUST** declare **exactly one** consistency mode from
   ADR-0004: `immutable`, `single_authority`, `causal`, `crdt`, `consensus`.
3. Peers **MUST NOT** treat the transport connection, libp2p stream, or prior
   request order as implicit state authority.

Full `StateRef@1` schema lands in MCPP-035; this binding only freezes the
**mapping rule**: current-binding handles → explicit `StateRef`, not session
memory.

Non-normative mapping sketch:

```json
{
  "stateHandle": "sh_01HZX…",
  "stateRef": {
    "mode": "single_authority",
    "ref": "urn:mcpp:state:…",
    "version": 3
  }
}
```

## 10. MCP Tasks map to MCP++ artifacts

The official MCP Tasks extension (`io.modelcontextprotocol/tasks`) provides
long-running work with methods such as `tasks/get` and `tasks/update`.

Under this binding, when MCP++ profiles are active:

| MCP Tasks concept | MCP++ mapping |
| --- | --- |
| Task id / task resource | References an execution artifact graph (envelope / receipt CIDs) |
| Task terminal output | Prefer Profile B artifacts: `output_cid`, `receipt_cid` (and related) |
| Task progress / intermediate state | MAY reference Event DAG event CIDs (Profile F) and/or `StateRef` handles (§9) |
| Task cancellation / failure | Portable error / receipt failure fields when Profile B is negotiated |

Rules:

1. Advertising `io.modelcontextprotocol/tasks` **does not** replace A2A Task
   for multi-agent handoff (ADR-0006).
2. Completing an MCP Task under MCP++ **SHOULD** leave durable evidence as
   CID-addressed artifacts rather than only ephemeral JSON in the task poll
   body when Profile B is mutually available.
3. DurableExecutor (ADR-0005) remains journal/recovery authority; it is **not**
   a public task lifecycle competing with MCP Tasks or A2A Task.

## 11. Transport vs MCP application binding

| Concern | Locus |
| --- | --- |
| This document (`mcp-binding/2026-07-28`) | MCP revision, `_meta`, discover, initialize rejection |
| Profile E / `transport-mcp-p2p.md` | libp2p stream protocol IDs, framing, peer discovery |
| HTTP / stdio | Official MCP transport pages for 2026-07-28 |

**libp2p stream negotiation is a carriage handshake.** It **MUST NOT** be
conflated with the removed MCP application `initialize` exchange. Opening a
`/mcp+p2p/…` stream **MUST NOT** be required as the only way to activate
Profiles A–D or F–H under this binding, and it **MUST NOT** reintroduce
session-level initialize semantics for current-binding claims.

When Profile E carries this binding, each framed JSON-RPC request on the stream
still **MUST** carry modern `_meta` as defined in §5.

## 12. Fail-closed rules (summary)

A peer claiming only `mcp-binding/2026-07-28` **MUST**:

1. Accept well-formed requests with `protocolVersion` `2026-07-28` **without**
   any prior `initialize`.
2. Reject `initialize` and `notifications/initialized` as current-path behavior
   (§4.2).
3. Reject missing required `_meta` keys (`-32602`).
4. Reject unsupported or forged protocol versions (`-32022` or equivalent
   fail-closed error).
5. Reject forged or mismatched binding id / version pairs.
6. Not invent session state from connection identity alone.

Dual-binding peers, silent downgrade, and cross-binding forgery matrices are
specified and tested in MCPP-022; they build on the positive and negative
proofs of this document and the legacy binding.

## 13. Interface checklist (`McpBinding20260728@1`)

An implementation may claim interface **`McpBinding20260728@1`** when it:

1. Uses binding id `mcp-binding/2026-07-28` and MCP revision `2026-07-28`.
2. Implements stateless per-request `_meta` with required keys in §5.2.
3. Implements `server/discover` and does **not** require it before other RPCs.
4. Rejects initialize-as-current (§4.2).
5. Advertises abstract profile keys per request and/or discovery (§6).
6. Maps multi-request handles to `StateRef` discipline (§9).
7. Maps MCP Tasks evidence to MCP++ artifacts when Profile B (and related) are
   active (§10).
8. Keeps libp2p/transport handshakes out of MCP initialize semantics (§11).
